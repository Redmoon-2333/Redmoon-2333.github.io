实验室要采购一台 GPU 工作站。查几家供应商的报价、核对机架尺寸和供电限制、提交申请，听起来是连着做的几件事。课件给了一个容易出错的版本：智能体串行查完四家，没找到完全合适的配置，却挑了一家提交。这里漏掉了三件事：几路报价本可以独立查，兼容性要等报价和内部规格都拿到才能判断，提交之前还要由人确认。这个案例贯穿了本课的四个部分：智能体怎样行动，怎样记住约束，怎样调整计划，以及多智能体怎样分工。

## 一、模型提出动作，Harness 负责执行

仓库、网页、应用和工作流都可以是智能体的环境。文件内容、截图、工具返回值是智能体已经拿到的**观察**；它们通常只暴露环境的一部分。模型根据观察提出下一步动作，动作经运行系统执行后，环境可能改变，也可能只返回一条信息。测试通过、任务评分或用户确认可以用来评价结果。一次读取成功是工具反馈，未必等于整项任务已经达标。

工具有名字、用途和参数约定。例如，下面两条是同一次只读调用的请求与结果示意，并非某个框架的消息规范：

```json
[
  {"id": "call_1", "name": "read_spec", "arguments": {"item": "机架规格"}},
  {"call_id": "call_1", "status": "ok", "data": {"max_height": "4U"}}
]
```

第一条由模型提出。运行层（Harness）解析调用，按 JSON Schema 等规则校验参数，再检查当前会话能否读取该资料。实际读取发生在工具侧；第二条才是返回给模型的观察。聊天模板可能用特定标记把这些结构编码进模型输入，不同模型的模板可以不同。标记能帮助模型区分消息类型，权限仍由运行层执行。

生成时的约束解码可以限制输出满足指定语法；用工具调用轨迹做监督微调（SFT），可以训练模型何时选择什么工具、怎样填写参数。格式有效、选对工具、目标对象正确、操作获准，是四件需要分别检查的事。调用结果回到上下文后，模型可以选择再读取一份规格、请求确认或结束。循环需要目标检查，也需要超时、轮数和重复失败上限；触及上限时应记录进展与尚缺条件，不能把停止写成成功。

## 二、运行一个智能体需要哪些层

| 组成 | 负责什么 | 回到采购案例 |
| --- | --- | --- |
| Harness | 管理工具、状态、记忆、控制流和错误处理 | 发起查询，关联每条结果，判断可以继续还是要暂停 |
| 执行隔离 | 约束工具能访问的文件、网络、凭证和计算资源 | 比价只需访问目录和授权的规格资料 |
| 推理服务 | 批处理、复用适用的 KV Cache、流式返回 | 管理排队、首 Token 延迟和吞吐；端到端耗时还受工具响应影响 |
| 训练系统 | 准备数据、采集轨迹、协调训练进程、保存和评估检查点 | 可用标注轨迹训练选工具或规划，这和现场执行分开 |
| 监控与评估 | 记录调用轨迹、权限决策、成本、耗时和失败原因 | 能追查候选在哪一步被淘汰、最终依据哪份规格 |

课堂把长上下文一致性、个人定制、复杂任务管理、理解环境和安全都列为智能体能力。以读编译报错为例：返回日志只解决“看到了什么”，模型还要知道错误指向哪个模块、接下来应该验证什么。可以用领域知识、专用工具或 Skill 给运行时补材料，也可以用领域轨迹训练模型。Skill 是一套可复用做法，用户记忆承载经确认的偏好；二者都不会自动给工具增加权限。隔离环境还方便从同一初始状态重跑评测。观察指标时，模型推理速度、工具延迟和任务完成率应分别记录。

## 三、记忆：保存事实，还是保存做法

课件把“把耳机加进愿望单”和“查无线键盘的价格区间”放在一起。两件事都要进入商店、找到搜索框、填查询词并搜索。复用的是到达结果页的流程，后面的读取价格或加入列表仍由当前目标决定。可以把共享步骤抽成技能，把某次查到的价格存成带时间的事实；如果下次需要审计当时做了什么，再回看完整轨迹。

| 记忆放在哪 | 适合保留 | 使用时的代价 |
| --- | --- | --- |
| 当前上下文 | 本轮目标、刚收到的观察和活跃的任务状态 | 输入变长会增加开销，旧细节也可能被噪声淹没 |
| 外部存储 | 可编辑、可检索的事实、案例和技能 | 需要筛选、去重、更新和管理访问权限 |
| 模型权重 | 经过训练形成的通用行为和能力 | 更新比改文件慢，难以追溯某条事实的来源 |

历史太长时，可以把已完成的过程压缩成摘要、按当前问题检索原始片段，或给独立子任务一份更小的上下文。摘要适合放目标和阶段结果；需要精确核对编号、报价或原话时，应保留回到原始记录的入口。子智能体返回结论时也要带证据和适用条件，主智能体不会自动拥有子任务看过的全部上下文。

课件第 20–23 页给了四种记忆用法。[MemGPT](https://arxiv.org/abs/2310.08560) 用层级存储和工具调用在有限上下文与外部记忆间搬运信息。[Mem0](https://arxiv.org/abs/2504.19413) 先取相似旧记录，再判断新增、更新、删除或不处理；例如有生效日期的新规格可以替换旧值，来源互相矛盾时先保留来源和状态，不能只按相似度覆盖。[Reflexion](https://arxiv.org/abs/2303.11366) 把一次尝试得到的反馈写成文本供下次使用，不在这一步更新模型权重。[ExpeL](https://arxiv.org/abs/2308.10144) 从经历中归纳提示，也可检索相似成功轨迹充当示例；经验库可以保留失败及其原因，检索时再决定哪种记录对当前任务有用。

## 四、把目标写成可以验收的步骤

一份计划要写明待完成的子目标、已有前提、依赖关系和验收条件。对当前候选集合，可以把采购任务写成下面的依赖关系。不同供应商的报价可以分别采集；核对配置既需要报价，还需要内部规格。

```text
查 A/B/C/D 的报价（可并行） + 读取内部规格
                    ↓
              兼容性与预算核对
                    ↓
                生成申请草稿
                    ↓
             人工确认后提交申请
```

若 A 要等 B 完成、B 也要等 A 完成，这两项在当前依赖定义下都启动不了。因此静态任务依赖可用有向无环图（DAG）表示。DAG 不排斥执行器有重试或条件分支：四家方案均不合格时，可以加入第五家或调整查询条件。必须放宽用户给定的硬约束时，应先把冲突交还给用户。

课件把思维链（CoT）视为一种轻量的规划形式：模型在同一次生成里展开推理并给答案。先分解再求解则把子问题单独写出来，让后一步读取前一步的结果。例如要查 1910 年出生的制片人参与制作的电影拿过哪些奖，可以依次查人物、确认制片关系、核对每部影片的获奖信息。人物筛选和实体关系查询可以交给不同处理器；早一步的错误也会传下去，所以要在交接时保留来源。参见 [Least-to-Most Prompting](https://arxiv.org/abs/2205.10625)。

经典规划要求更明确。[PlanBench](https://arxiv.org/abs/2206.10498) 所用的形式化思路把状态写成谓词，把动作写成前置条件和效果。以课件的积木世界为例，“拿起桌上的积木”要求手空、积木在桌上且上面没有挡物；执行后，手里有积木，“手空”和“积木在桌上”不再成立。规划就是从初始状态找一条每步可执行、末尾满足目标的动作序列。自然语言计划容易表达模糊目标，形式化动作适合自动核对。程序能写出分支、循环和外部调用，仍要检查它依赖的观察是否准确、接口是否执行了预期动作。

## 五、边做边看：什么时候值得重规划

开发者预先规定工作流时，程序按既定顺序运行；先规划再执行时，模型能给每个任务生成不同的步骤；自适应执行还会在拿到新观察后修订剩余步骤。供应商页面明确标出缺货时，原计划的候选排序就要重算。页面一次临时读取失败时，有限重试可能比推翻整个计划更合适。已经核实的结果应随计划版本保留。

把规划器与执行器分开后，两者可以用不同的数据训练。课件的 GUI 例子里，规划器说“在页首搜索框搜索 4K 显示器”，定位模块把这个描述对应到当前截图中的可操作位置，执行器再输入内容。[Plan-and-Act](https://arxiv.org/abs/2503.09572) 展示了用教师模型给执行轨迹切分、标注子目标，再分别训练规划器和执行器的思路。分工的前提是上一模块给出的目标、观察和返回格式足够明确。

在机器人场景，动作还要符合当前环境和机器的能力。[SayCan](https://arxiv.org/abs/2204.01691) 将语言模型给出的任务相关性与技能在当前状态下的可行性评分结合起来，对候选动作排序。简化示例：直接拿苹果的相关性为 $0.9$、可行性为 $0.1$，乘积为 $0.09$；先打开已定位的储物柜，两项分别为 $0.6$ 和 $0.8$，乘积为 $0.48$。在这两项候选中先选开柜，看到苹果后再更新判断。数字只演示打分规则，不是论文实测。

课件还对比了“多想一会儿”和“先观察一次”。遇到不熟悉的表格格式，与其猜测表头、分隔符，再反复分析出错原因，不如先做一次只读预检。[Calibrate-Then-Act](https://arxiv.org/abs/2602.16699) 把这类选择写成获取信息的成本与错误行动的代价之间的权衡。课堂提到的三种失败也有相应的检查点：

| 现象 | 该检查什么 |
| --- | --- |
| 分析瘫痪 | 多轮讨论后是否还没有新增观察或可核验产物 |
| 动作链失序 | 被同时启动的动作是否真的独立，是否超过并发和资源上限 |
| 过早结束 | 提交“完成”前，目标状态是否有测试、环境回执或人工确认 |

## 六、长任务：及早发现错误，交接时传递证据

课件用 [Vending-Bench](https://arxiv.org/abs/2502.15840) 说明错误会在后续决策里持续影响状态：把“预计今天送到”当成“已经收到”，补货、库存和经营判断就会在同一个错误前提上继续。长任务需要在高影响节点停下来核对事实，在能够纠正的阶段修复；另一个模型可以参与复核，但它与执行模型的错误可能相关。能用结构化数据、测试或回执核对时，应优先用这些可独立检查的证据。

设一条固定计划有 $n$ 步，任何一步失败都会使整项任务失败。令 $E_i$ 表示第 $i$ 步成功，按条件概率连乘：

$$
P(E_1\cap\cdots\cap E_n)
=P(E_1)\prod_{i=2}^{n}P(E_i\mid E_1,\ldots,E_{i-1}).
$$

如果在此前各步都成功的条件下，每一步的成功率都等于 $p$，整条链的成功率才简化为 $p^n$。下面是这个假设下的手算值：

| 每步成功率 | 10 步全部成功 | 50 步全部成功 | 100 步全部成功 |
| --- | ---: | ---: | ---: |
| $98\%$ | 81.7% | 36.4% | 13.3% |
| $99\%$ | 90.4% | 60.5% | 36.6% |

这一算例只说明复合效应。真实轨迹有依赖、重试和恢复，模型还可能把自己先前的错误输出当作新前提。[长程执行研究](https://arxiv.org/abs/2509.09677) 讨论了这类对自身历史的依赖。除了最终成功率，记录首个偏差在哪出现、何时被发现、是否可以恢复，更容易判断问题出在计划、执行还是检查。

预算、权限和禁止改动的范围是全局条件。两路查询并行时，不能各自把整笔预算当作自己的额度；若下游需要提交申请，访问报价的授权也不能代替提交授权。运行层应校验允许的动作和参数。网页与工具输出可以提供价格、库存等数据，里面出现的文字不能自行扩展任务范围。固定动作集合、按需审批和最小访问权限共同约束副作用，审计记录则用于追查实际发生的行为。相关课件例子见第 50–51 页。

## 七、多智能体协作：把分工和交接设计清楚

把独立子任务分给多个 Agent，可以缩短等待时间，但发送上下文和汇总结果都会产生额外开销。在本来就有多个参与方的环境里，每个 Agent 还可能拥有不同的观察、职责和权限。课件用以下几种组织方式说明这一点：

| 组织方式 | 怎么交换信息 | 适合在哪一步用 |
| --- | --- | --- |
| 固定角色流程 | 设计、开发、审查、测试按协议交付草稿、代码和反馈 | 阶段和责任已知，如课件的 ChatDev 案例 |
| 多智能体辩论 | 先各自提出答案，再互看依据并修订 | 结论有歧义，需要比较推理；达成一致后仍要核对证据 |
| 按需委派 | 主 Agent 发派子目标，子 Agent 返回证据和小结 | 并行查不同供应商、独立核对经费和规格 |
| 中心化异步编排 | 管理者维护任务 DAG，经结构化消息分派，用独立工作区和 Git 汇总 | 有依赖和合并冲突的多人式协作 |
| 去中心化协作 | 公共队列标明任务归属，成员在只追加的共享板上提交带类型的消息和产物 | 多个独立参与方协商，各自掌握不同局部信息 |

课件展示了按需递归委派：子 Agent 发现任务还可拆分时继续委派，最终逐级汇总。应在启动前规定深度、并发数和总预算，拆到交接成本接近任务本身时就没有必要继续开分支。角色设计也决定谁能看见哪些材料。负责归并的 Agent 需要验收结果和分歧，通常不需要复制每个子任务的完整日志。[ChatDev](https://arxiv.org/abs/2307.07924)、[Recursive Agent Optimization](https://arxiv.org/abs/2605.06639)、[异步软件工程协作](https://arxiv.org/abs/2603.21489) 和[共享上下文的去中心化协作](https://arxiv.org/abs/2606.10662) 分别讨论了这些组织方式。

课末把人也放回系统：用户可以提供偏好、补充约束和确认有副作用的动作。用户模拟器可用于训练和评估交互策略；课件还给了[模拟市场](https://arxiv.org/abs/2510.25779)与[模拟小镇](https://arxiv.org/abs/2304.03442)两个例子，分别观察多方搜索、交流与交易，以及角色如何用记忆和反思安排日常活动。模拟能提供可复跑的环境，得到的结论受模拟规则和角色设定限制。

## 八、复习：把工作站案例走一遍

1. **查到报价就可以提交吗？** 报价只是一项观察。还要检查兼容性、预算和报价有效期，形成申请草稿并取得提交所需的授权。
2. **四家都不合适，下一步是什么？** 保留已核实的报价和淘汰原因，再考虑增加候选、刷新缺失信息或请用户调整硬约束。无需把已经验证的工作全部重跑。
3. **新的价格与记忆不一致，哪个拿来用？** 先核对商品标识、来源、生效日期和币种。能证实新报价替代旧报价时更新；证据仍冲突时，把差异保留到复核。
4. **两个 Agent 都说“可以提交”，能算验收吗？** 两个答案是两条判断。提交的依据仍是规格与预算核对结果，以及对应操作的授权记录。
