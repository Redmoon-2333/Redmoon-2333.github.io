工单写着「检查完成后才能搬运」。让冻结的语言模型直接派单，它既要读懂这层依赖，又要算谁有资格接单、什么时候能开工。也可以让它只填一份结构化工单，再由程序枚举排程。40 道新题里，后者做对 40 道，直接派单补跑合并后做对 39 道。两者的成本见第 4 节。

检查从 9:00 开始，要做 20 分钟。搬运员 9:10 就空闲，但搬运得等到 9:20。结构化工单在检查项记 `时长=20 分钟`，在搬运项记 `前置=检查`；调度器用 `max(9:10, 9:20)` 算搬运开工时间。若系统排在 9:10，先查搬运项有没有填前置，再查调度器有没有用它。

## 1. 故障之后，不一定要全队重排

作者公开调度数据的复算与本地模拟比较了固定分工、相信报告、校准后改派等策略。

办公室没有故障时，固定分工代价为 10.51，校准后改派为 12.34；长故障时，两者为 56.61、36.71。是否改派取决于等待损失能否覆盖调整成本。

这组结果来自公开数据与模拟调度。作者按任务等权统计正确性，得到 0.948276。每个任务的日志条数不同时，按所有日志合并计算会改变任务权重。

## 2. 报告内容、真假和来源

32 条不同故障通知中，3B 模型换选项顺序后的正确数为 18/32、26/32，词法规则为 30/32。后续远程模型的通知重测为 31/32、32/32。

「预计迟到 10 分钟」可以标为延误通知。报告是否属实还需要实际到达时间，两条相似通知是否独立则需要来源记录。三个标签分别由文本、运行记录和来源信息提供。

另一组复核包含 40 个已判正确方案和 7 个未评分方案。模型把 38 个已知正确方案也送去人工复核，因此这组正确方案的误报率为 `38/40=95%`。要算坏计划召回率，分母应是已知坏计划的总数；这批没有这一类标注。

## 3. 单字母派单与允许推理，结果会不同

96 条资源约束派单请求中，限制只输出字母时，远程模型答对 65 条、本机 3B 答对 28 条，规则求解为 96 条。允许远程模型核对条件并给出推理后，同批达到 96/96。

同一批题、同一远程模型，改动输出协议后从 `65/96` 到 `96/96`。复用这个结果时，两种协议的采样和推理成本也要分别记录。

## 4. 五工序：抽取＋求解的比较

新任务包含五道工序、四名成员、技能与区域权限、速度和前置依赖。规则规定按 T1–T5 的拓扑次序排入每人的日程，目标是最小完工时间。

| 方法 | 40 道新题结果 | 输入＋输出 token 约值 |
|---|---:|---:|
| 大模型直接派单，合并截断重跑后 | 39/40 | 2,016/题 |
| 大模型抽取 JSON＋精确枚举 | 40/40 | 619/题 |
| 按最快合格成员贪心 | 25/40 | 0 |

表中 2,016 是补跑后保留回复的均值。计入被替换的原调用和补跑，40 次原调用加 13 次补跑共 111,180 token，即实际记录成本 2,779.5 token/题。枚举求解还使用 CPU，表中的 token 只计模型调用。

直接派单的初测为 27/40，表中 39/40 来自补跑后合并的评分。中档模型两次抽取都正确且一致，每次约 1,774 token/题，抽取成本比表中的大模型配置高。

3B 完整抽对的工单为 0/40，其中 37 题抽错前置依赖。求解器会把这些依赖当成工单条件，抽取错误会随之进入排程。

「能读入 JSON」和「把工单抽对」是两项检查。拿开头的搬运工单来说，`{"id":"搬运","after":[]}` 是合法 JSON，但空列表会让求解器以为搬运可以先做。先检查字段能否解析、编号是否存在，再用原文核对「先检查、后搬运」有没有进入 `after`。第 5 节的求解代码只接收核对后的字段。

## 5. 求解器的核心逻辑

纸上工单有三道工序。甲能在南北区检查，速度为 2。乙在北区能检查和搬运，速度为 1。耗时为工作量除以成员速度。

| 工序 | 要求 | 工作量 | 前置 |
|---|---|---:|---|
| T1 | 北区检查 | 2 | 无 |
| T2 | 南区检查 | 4 | 无 |
| T3 | 北区搬运 | 2 | T1、T2 |

若每次挑最快的合格成员，甲从时刻 0 做 T1，到时刻 1 才开始 T2，在时刻 3 完成。乙随后搬运，时刻 5 完工。把 T1 改派给乙，甲可以立刻做 T2，两项检查都在时刻 2 完成，乙继续搬运，时刻 4 整单结束。

下面保留原实验的枚举和排程逻辑，数据缩到这张工单。`after` 存前置工序编号，工序按前置在先的顺序提供。

```python
import itertools

def qualified(task, worker):
    return (
        task["skill"] in worker["skills"]
        and task["zone"] in worker["zones"]
    )

def makespan(tasks, workers, plan):
    free_at = dict.fromkeys(workers, 0)
    done_at = {}
    for task in tasks:
        name = plan[task["id"]]
        worker = workers[name]
        if not qualified(task, worker):
            return None
        ready_at = max((done_at[t] for t in task["after"]), default=0)
        start = max(free_at[name], ready_at)
        end = start + task["work"] / worker["speed"]
        done_at[task["id"]] = free_at[name] = end
    return max(done_at.values())

def solve(tasks, workers):
    best = None
    for assignment in itertools.product(
        workers, repeat=len(tasks)
    ):
        plan = {
            task["id"]: name
            for task, name in zip(tasks, assignment)
        }
        finish_time = makespan(tasks, workers, plan)
        if finish_time is not None:
            if best is None or finish_time < best[0]:
                best = (finish_time, plan)
    return best

workers = {
    "甲": {"skills": ["检查"], "zones": ["南", "北"], "speed": 2},
    "乙": {"skills": ["检查", "搬运"], "zones": ["北"], "speed": 1},
}
tasks = [
    {"id": "T1", "skill": "检查", "zone": "北", "work": 2, "after": []},
    {"id": "T2", "skill": "检查", "zone": "南", "work": 4, "after": []},
    {"id": "T3", "skill": "搬运", "zone": "北", "work": 2, "after": ["T1", "T2"]},
]
print(solve(tasks, workers))  # (4.0, {'T1': '乙', 'T2': '甲', 'T3': '乙'})
```

`makespan` 返回工单总完工时间。拿最优分配里的 T3 逐行对照：乙到时刻 2 才空闲，T1、T2 也都在时刻 2 完成，`max(2, 2)` 得到开始时刻。T3 的工作量为 2、乙速度为 1，再加 2 工时，整单时刻 4 完成。求解器按 `after` 里的依赖算，工单少填一项，程序就会按另一道题排程。

原任务的四名成员和五道工序共有 $4^5=1024$ 种分配，可以全枚举。最优性覆盖这些分配在固定排程次序下的得分。

这里枚举的是「每道工序给谁」。例如同一个人可以先检查 T1 再检查 T2，还是反过来，程序由输入工序顺序决定。若实际工单还允许自由调整先后，就得把排序也纳入求解。

## 6. 大模型拆题，小模型执行：步骤越细不一定越好

沿用 E4 的 400 道数学题，大模型生成 2–5 个子问题：

- 把计划作为提示，小模型由 84.25% 到 88.25%，改对 38 题、改错 22 题。
- 要求小模型严格逐步执行，降到 62.5%，常见错误是把子问题对应到了错误的量。
- 只改派第一个分歧步骤，整体为 84.0%；97/137 是失败条件内的救回数，还使用了大模型参考轨迹。

要判断分段为何失效，可以先核对小模型读到了哪个量，再检查它有没有把局部答案原样带到下一步。前一环出错会改变后面看到的子问题。

## 7. 复核没结束，能不能先开工

另一个模拟枚举复用了 40 张工单，研究依赖尚未核实时，是否存在对所有候选依赖图都安全的首派。等待设为 2 工时，14 张多候选工单中，相对最强零误派对照多赢 1 张，平均多省约 0.071 工时，未过预设门槛。

若两个候选都允许先检查，检查就能在复核的 2 工时内开始；只要其中一个候选要求先断电，就得等确认后才能派检查。这里统计的是模拟工时内省下的等待与首派是否合法；线上 API 延迟用真实请求计时。
