查店铺里有多少条评论提到 `satisfied`，需要找到评论页、填入关键词，再读取结果。下次换成 `great`，值得留下的是查评论的方法，上一次找到的数量已经用不上了。这个区别引出本课的三条线：Skill 把做过的事整理成可复用的步骤；MCP 给宿主提供发现和调用工具的接口；代码大模型把需求变成程序，程序能否交付还要靠测试来判断。

## 一、从完成一次任务到留下一个 Skill

一条轨迹记录某一次做过的动作，例如进入后台的 Marketing，打开 All Reviews，向编号为 `757` 的输入框填入 `satisfied`，触发搜索。轨迹保留了当时的页面与参数，适合追查这次发生了什么。提炼成 Skill 时，要保留能复用的步骤，把关键词改成参数 `term`，并说明入口条件和成功标志。后台如果重新布局，`757` 就可能指向别的控件；跨环境复用时，需要把「找评论搜索框」和「本页用哪个控件」分开。

| 保存形式 | 评论检索的例子 | 取用方式 |
| --- | --- | --- |
| 完整轨迹 | 具体页面、动作、关键词和返回结果 | 作为示例参照，也可用于定位当时的错误 |
| 文本 Skill | 打开评论页，输入 `{term}`，核对筛选条件后读取数量 | 模型读到步骤后，按当前页面逐步执行 |
| 代码 Skill | 可调用的 `search_reviews(term)`，内部完成定位与查询 | 执行器调用函数，还可以写测试、与其他函数组合 |

文本步骤便于应对不同页面；代码把稳定的低层动作交给执行器，模型不必为每一次点击重新决策。在课件的商品搜索例子里，`search_product` 把点击搜索框、输入查询词和回车封装起来。页面改版后，文本 Skill 仍能指导模型观察新页面，而代码需要更新定位逻辑。第 15 页的 [PolySkill](https://arxiv.org/abs/2510.15863) 把这种分工做成两层：上层组合流程只依赖抽象方法，环境分别实现搜索、选项定位等原语。新网站可以沿用上层流程，前提是它能提供这些原语的等价操作。

课件在这里用 Skill 指从经验中归纳的可复用行为。[Agent Skills 规范](https://agentskills.io/specification) 则约定了如何交付一份技能包：`SKILL.md` 写名称、说明和步骤，按需附脚本、参考资料或资源。一个技能包可以同时包含文本指引和可执行代码。Voyager 把游戏中的动作序列累积成可组合函数；DreamCoder、Stitch 等工作从解过的程序中抽取反复出现的结构。这些是课件用来交代「复用」思路的历史例子。

## 二、Skill 怎么入库，又怎么用到下一次

1. **判断轨迹。** 根据环境终态或规则判断任务是否完成。查询页回了结果，还要核对关键词、筛选范围和计数单位。
2. **抽取候选。** 从相关轨迹找共用子步骤，把关键词、日期等变化项参数化。只在某一任务中出现的业务判断留在该任务里。
3. **验收入库。** 在已有任务和变体上试跑，看候选是否实际被调用、原任务是否仍完成。代码还能先做静态检查：例如函数收了 `color` 参数却未在函数体内使用，调用者即使传入颜色也不会触发对应筛选。
4. **检索与维护。** 新任务到来后优先取少量符合前置条件的 Skill，执行时检查结果。接口变更或反复失败时，修订实现、补回归测试，必要时停用旧版本。

课件第 12 页对比了同一个更新账单地址和收货地址的任务：无记忆基线走到 **50 步上限后终止**；代码 Skill 版本在该示例中用 4 步完成。一个 Skill 调用内部仍能执行多个浏览器动作，因此这里比较的是论文记录的智能体步数，实际等待时间还取决于内部操作和页面响应。第 13 页引用的 [ASI 表 4](https://arxiv.org/html/2504.06821v2#S4.T4) 汇总了浏览器任务的结果：

| 配置 | 检查点达成率 | 平均步数 |
| --- | ---: | ---: |
| 无记忆 | 41.3% | 24.5 |
| 文本 Skill | 59.5% | 20.6 |
| 代码 Skill | 80.2% | 15.0 |

表中数字是对论文五个场景的指标做的等权平均。文本 Skill 一行对应论文里的 AWM，代码 Skill 一行对应 ASI。「达到某个检查点」与「完成整项任务」是两种口径；部分步骤做对，仍可能没有保存两个地址。

### 失败经验、检索数量和维护责任

失败轨迹适合提炼条件和纠正办法，例如「切换日期后再读取数量；仍显示旧筛选条件时先刷新结果」。直接保留失败动作序列，后续模型可能把它当作下一次的照做范例。课件第 18 页的 [ReasoningBank 对照](https://arxiv.org/html/2509.25140v1#S4.SS3) 中，从只使用成功轨迹改为同时使用失败轨迹，ReasoningBank 的成功率由 46.5% 升到 49.7%，同一对照中的 AWM 由 44.4% 降到 42.2%。第 19 页还介绍了用固定概率翻转真实标签的模拟评判器，用来观察评判质量如何影响经验库。评判器适合给候选排序；有可查的页面终态或可执行测试时，直接用这些证据核验更稳。

检索也有成本。塞进更多相似经历会占用上下文，还可能带入失效的页面路径。已知的业务规则和高代价动作适合由人定义验收标准；频繁重复、结果又容易检查的工作流适合让智能体归纳和试跑。技能要留维护人，遇到页面变化时才能决定改哪一层。

单次任务成功，只说明它当时做对了。第 21 页把后续任务也放进同一条训练样本：第一次购物任务把 `search(query)` 写入记忆，第二次查键盘价位时读取并实际使用它。课件给出的第一项任务奖励示意是：

$$
R_1 = r_1 + \mathbf{1}[\text{both succeed}] \cdot \mathbf{1}[\text{task 2 reuses skill}].
$$

$r_1$ 衡量第一次任务的结果；只有两个任务都成功、且第二次实际复用了该技能，才给额外奖励。这样可以区分「第一次做成功」和「第一次留下的办法在后续用上了」。

## 三、从模型生成调用到工具真正执行

课件用天气查询说明工具调用。宿主先向模型提供工具名称、用途和参数模式；模型在输出里给出工具名和参数。不同模型或推理 API 会用不同的模板编码这些内容。下面是宿主与模型之间的一组教学消息：

```json
[
  {
    "id": "call_1",
    "name": "get_weather",
    "arguments": {"city": "上海", "units": "C"}
  },
  {
    "call_id": "call_1",
    "result": {"temperature": 18, "units": "C"}
  }
]
```

第一条是待执行的请求，第二条才是对应的工具结果；18°C 是示意数据。课件以 OpenHands 说明分发过程：先注册可调用工具，再解出模型请求，按名称选实现，校验参数与权限，调用执行器，把结果用调用 ID 关联回模型。格式正确也可能查错对象，比如把「上海」填成「苏州」。运行层能检查输入结构，任务层还得核对城市和温标是不是用户要的。

### REST、OpenAPI 和 MCP 各管哪一段

| 接口或规范 | 解决的问题 | 天气查询中的位置 |
| --- | --- | --- |
| 进程内函数 | 程序怎样调用本进程的能力 | 直接调用天气库函数 |
| REST API | 客户端怎样通过 HTTP 请求远端服务 | 向天气服务发送带城市和单位的请求 |
| [OpenAPI](https://spec.openapis.org/oas/v3.1.1.html) | 怎样描述 HTTP 操作、参数、返回值和鉴权方案 | 描述天气查询端点 |
| [MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) | AI 宿主怎样发现并调用服务端提供的工具 | 发现 `get_weather`，再按工具模式传入参数 |

宿主可以直接接 REST API，也可以由 MCP 服务端把已有 API 包成工具。按 MCP `2025-11-25` 版规范，宿主中的客户端在连接初始化后，可用 `tools/list` 获取工具名称、说明和输入模式，再用 `tools/call` 发送调用。下面是后一步的 JSON-RPC 请求，`id` 用来配对这次协议请求和响应；上例里的 `call_1` 属于宿主与模型的消息，两种 ID 由不同层管理。

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"city": "上海", "units": "C"}
  }
}
```

课件演示了 [FastMCP 从 OpenAPI 映射工具](https://gofastmcp.com/docs/integrations/openapi) 的做法。天气服务仍走原来的 HTTP 接口，MCP 服务端负责转换参数和结果。接入时可以让客户端只持有访问 MCP 服务的凭证，由服务端单独管理上游天气 API 的凭证。哪些操作对当前用户开放、什么时候需要确认、错误怎么传回宿主，仍要由具体系统落实。MCP [传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) 描述了 `stdio` 和 Streamable HTTP；它们承载协议消息，不决定工具如何调度。

## 四、哪些工具能并行，怎样评价整条轨迹

读天气、读日历、查航班状态，三者都已拿到各自的查询参数、也不修改共享状态时，可以分开执行。查顾客 ID 后才能用它获取订单，这是**数据依赖**；确定所选订单并得到确认后才允许退款，这是**控制依赖**。两个调用也可能读写同一份库存或地址，即使参数彼此独立，执行顺序仍会影响结果。并行判断同时看参数来源、执行条件和共享状态。宿主还需要给调用设超时、区分哪些失败可重试，并在部分结果缺失时如实交接。

| 评价层次 | 检查内容 | 常见错误 |
| --- | --- | --- |
| 工具选择 | 有没有选对工具，是否漏调或多调 | 查实时天气时选了历史气候统计 |
| 参数 | 字段、类型与业务值是否正确 | 单位是合法枚举，却填成用户没要的华氏度 |
| 执行轨迹 | 调用顺序和依赖是否合理 | 未取得订单就尝试执行退款 |
| 端到端任务 | 最终结果是否满足用户目标 | 调用成功，却把另一个时间段的结果当成今天的结果 |
| 运行表现 | 在时延、成本、限流和部分失败下是否可用 | 一路超时导致其他已经成功的结果也没能交付 |

静态匹配可检查工具名、参数结构和一部分参数值。有多个正确的执行顺序时，重点是依赖有没有满足，不能只按一条参考序列逐项比对。课件用 [Berkeley Function Calling Leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html) 作为工具调用评测实例。生产检查还要看真实调用的超时、重试、权限和副作用，才能把「输出写对了」和「事情办成了」分开。

## 五、写代码之前，先把冲突写进需求

课堂上举了两条智能窗户规则：温度读数高于 10°C 时开窗，下雨时关窗。如果读数为 12°C 且正在下雨，两条规则会同时发出相反命令。代码可以实现任一种优先级，谁优先要先与需求方说清楚。需求工程做的就是收集需求、建模、协调冲突、写清约定、核验是否符合原意，并在要求变化时同步维护规格和测试。

下面采用「雨天优先，干燥时严格高于 10°C 才开窗」这一教学约定。刚好 10°C 是边界，12°C 下雨是冲突用例。

| 温度读数 | 下雨 | 预期指令 |
| ---: | --- | --- |
| 9°C | 否 | 关 |
| 10°C | 否 | 关 |
| 12°C | 否 | 开 |
| 9°C | 是 | 关 |
| 12°C | 是 | 关 |

```python
def window_command(temperature_c: float, raining: bool) -> str:
    if raining:
        return "close"
    return "open" if temperature_c > 10 else "close"


assert window_command(9, False) == "close"
assert window_command(10, False) == "close"
assert window_command(12, False) == "open"
assert window_command(9, True) == "close"
assert window_command(12, True) == "close"
```

这里的预期结果由需求表独立给出。若改成「雨天保持现状」，接口就得能表达 `keep`，下雨的测试也要跟着改。旧实现通过旧测试，不能替代对新规格的验收。

## 六、从生成候选到验证补丁

写代码的任务可以先让模型提炼接口、状态和边界条件，再生成实现。给少样本示例时，应选与当前输入输出或 API 用法匹配的示例；仓库任务还要先读取周边代码和实际依赖接口。课件用软件中的重复结构解释为什么已有实现值得检索，也对照了按形式化规则构造程序和「生成候选，再用测试淘汰」两条路线。后一条允许试多个候选，筛选精度由规格和测试覆盖决定。

反馈来源有各自的用途。模型解释逐行意图时能帮忙发现遗漏分支；报错、类型检查和实际运行能确认候选在当前环境的行为；用户反馈用来决断尚未写清的需求。仍以窗户为例：如果 10°C 的用例失败，先在阈值比较处定位，核对是否把 `>` 写成了 `>=`；修改后同时跑边界用例、雨天冲突用例以及旧的正常路径。补丁如果没有通过，新的失败信息又可以缩小定位范围。这是课件末尾所说的**定位与修复相互反馈**。

测试生成分三件事：写运行测试的代码、挑能区分行为的输入、为每个输入给出可信的预期结果（test oracle）。模型若照着错误实现生成预期结果，会把同一个错误写进测试。用边界值、互斥条件和真实调用场景选输入，用需求或独立参照实现确定预期结果。静态检查在不运行程序的情况下发现类型、接口和部分代码质量问题；动态测试负责观察具体执行路径。课件的安全评估部分还提醒，代码应按实际约束做审查，模型给出的缺陷判断也要用代码和测试复核。

## 七、代码评测看的是哪一种正确

[HumanEval](https://arxiv.org/abs/2107.03374) 给函数签名、说明和单元测试，检查生成的函数能否通过测试。候选较多时用 $\mathrm{Pass@}k$ 表示抽取 $k$ 个候选、至少一个通过的概率。对一个题目有共 $n$ 个候选样本，其中 $c$ 个通过，且 $1 \le k \le n$，论文采用的估计式为：

$$
\widehat{\mathrm{Pass@}k} = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

分式数的是从样本中挑出的 $k$ 个候选全部失败的比例，若失败样本不足 $k$ 个，分子为零。举例：5 个候选只有 1 个通过，抽 2 个至少抽中一个通过的概率是 $1-6/10=0.4$。报告多题成绩时再对各题求平均。比较时要看同一采样预算和测试口径；实际部署若只能交一个候选，还需说明怎样从多个候选里选出它。

| 评估对象 | 对应基准或问题 | 能回答什么 |
| --- | --- | --- |
| 小型函数 | HumanEval | 给定签名和说明，能否生成通过单元测试的函数 |
| 更强的功能检验 | [EvalPlus](https://arxiv.org/abs/2305.01210) | 增加测试输入后，原本通过的程序是否仍正确 |
| 真实仓库改动 | [SWE-bench](https://arxiv.org/abs/2310.06770) | 给定实际项目及问题说明，补丁能否让目标测试通过并保住原有测试 |

正确率之外，还有三项容易混在一起。**鲁棒性**考察等义改写提示、变更无关上下文后，候选行为是否仍满足同一需求；**确定性**考察保持输入和配置一致时，多次生成的输出有多稳定。两段不同的代码可以通过同一套测试，所以「字符一致」与「行为一致」适合分别统计。**可解释性**看能否说清假设、关键分支和证据，例如指出雨天分支为何放在温度比较之前，并给出对应测试。解释文本要能回到代码与执行结果。

课件最后用端到端开发与维护作拓展。把需求、代码、测试和故障修复放进同一条流程后，每个环节都应给下一环节可核对的东西：需求给验收条件，代码给可运行的候选，测试给失败输入和预期结果，补丁给回归记录。窗户例子最终交付的判据是这五类输入下的指令符合约定；改动优先级时，从规格和测试一起改起。
