## 一、离开浏览器以后，成功没有统一的含义

Web 验证还能从页面内容获得直观反馈，非 HTTP 服务则需要理解协议状态。数据库返回欢迎包、文件共享返回导出名称、视频服务返回媒体描述，分别说明不同的事情。

训练后期的协议记录覆盖了数据库、SMB、FTP、LDAP、SNMP、NFS、RTSP、远程桌面和设备管理面。最有用的整理方式，是为每种协议建立能力层级：连接、协议识别、认证、资源读取、状态改变。工具写出的 `SUCCESS` 要映射到其中某一步。

| 协议或服务 | 常见观察 | 需要保留的边界 |
|---|---|---|
| 数据库 | 握手、版本、认证结果 | 握手成功不等于登录，更不等于读取了库表 |
| FTP、SMB | 匿名身份、共享或目录元数据 | 登录、列目录、读文件与写文件是不同能力 |
| LDAP | 匿名绑定、服务根元数据 | 根元数据可见不等于可枚举全部目录对象 |
| SNMP | 设备状态、管理信息 | 可读信息与写配置分别判断 |
| BMC、Redfish、虚拟化平台 | 服务根、管理页面、会话 | 页面与元数据可见不等于控制宿主机 |
| RTSP | 会话描述、媒体控制状态 | 描述返回不等于媒体已经播放 |

这里列的是判读框架。具体设备是否存在安全问题，还取决于哪些信息本来允许公开，以及历史事务实际证明到了哪一层。

## 二、NFS：导出清单和文件内容之间还有几道检查

NFS 复核是这次训练中很有代表性的协议案例。早期观察看到导出清单与通配标记，容易联想到“任意主机可以访问”。后续记录却显示，部分导出在实际挂载阶段返回了拒绝。

在 NFSv3 配套的 MOUNT 协议中，EXPORT 返回导出目录与相关客户端组信息；MNT 是请求挂载句柄的另一项操作。〔1〕 因而，读取导出声明和取得访问句柄不能混为一谈。

| 阶段 | 本阶段的意义 | 合适的表述 |
|---|---|---|
| 服务查询 | 发现相关 RPC 服务 | 服务可识别 |
| EXPORT | 得到导出清单 | 导出元数据可查询 |
| MNT | 请求文件句柄 | 按返回结果说明获得句柄或被拒绝 |
| 目录操作 | 请求目录条目 | 仅对实际返回的范围说明可列举 |
| 文件读取 | 请求文件内容 | 需要相应内容证据及允许的验证范围 |

历史复核记录中的一个典型结果是：导出声明看似宽泛，但 MOUNT 返回状态 13。按 RFC 1813 的 MOUNT v3 定义，这是 `MNT3ERR_ACCES`，即访问被拒绝。它支持“此次挂载请求被拒”，不能从中直接推出后台采用了哪一种安全配置。

这也纠正了一个容易忽略的术语细节：MOUNT 状态和 NFS 操作状态属于相关但不同的枚举。即使数字含义相似，报告仍应写明它来自哪一层响应。

## 三、协议解析器本身也可能出错

同一份 NFS 复核材料记录了帧长度和 XDR 结构理解方面的问题。若请求帧构造错误，服务器可能不按预期应答，外部看起来像超时；若解析时把链表当作计数数组，结果可能静默丢失后续字段。

这种故障比明显抛出异常更难发现，因为输出仍像一张合法表格。验证自写解析器时，应把原始字节、协议规范和解析后的结构放在一起，检查长度、对齐、边界与剩余数据。

RFC 1813 中的 EXPORT 结构包括目录、客户端组链表和下一节点，没有提供完整的服务器导出选项清单。〔1〕 因此，缺少某个配置字段时，应先检查协议是否会传输该字段，不能自动归因于解析失败，也不能凭空补出配置。

这个经验可以迁移到其他二进制协议：解析结果越“像真的”，越需要用已知样例和规范确认字段位置。

## 四、RTSP：会话描述能说明什么

历史材料中有 RTSP `DESCRIBE` 返回 SDP 的记录。SDP 描述媒体类型、编码和相关参数，它说明服务器提供了会话描述。

RTSP 的 DESCRIBE、SETUP 和 PLAY 承担不同任务：获取描述、配置传输、控制播放。〔2〕 后面的操作可能有各自的认证要求。因此，返回 SDP 可以用于分析描述信息是否暴露，不能直接证明匿名观看画面已经成立。

DESCRIBE 也不应简单写成“等价于 HTTP HEAD”。HEAD 在 HTTP 中不返回响应内容，而 DESCRIBE 的用途恰恰包括返回媒体描述正文。〔2〕〔3〕

这种差异会改变报告结论。若历史验证停在描述阶段，恰当的总结就是“得到媒体描述，播放权限未由这次记录建立”。说明本次能力层级，就已经足够支持相应分析，无需用更强的措辞填补缺失步骤。

## 五、设备管理面与业务面要分开

打印机、NAS、虚拟化平台和带外管理控制器，在同一网络里可能同时提供 Web 页面、文件共享和管理协议。一个设备的多个端口可以对应不同功能，也可能共同暴露同一份配置。

因此，查重时既不能只看主机，也不能只看端口。需要问：是否同一资源？是否同一种访问控制缺失？修复是否会同时解决两个现象？

例如，设备状态页公开了型号和耗材信息，与后台能够修改网络参数，是不同的能力层级；同一信息被两个接口返回，也未必构成两个独立问题。报告应围绕实际影响和根因组织，而不是围绕扫描器发现了几条路径组织。

文件共享也类似。匿名 FTP 可能用于公开分发，是否构成风险取决于返回内容、预期用途与权限配置。看到匿名登录成功，应先确认这一步的含义，不能默认存在敏感数据泄露。

## 六、把每一次“成功”展开

后期历史认证审查中，同一事件既写入主日志，也被投影到 HITS 文件。两份文件并不代表发生了两次独立认证；客户端标签也不能自动证明目标身份与权限等级。

更可用的记录方式是保留协议状态和所处阶段，例如“收到认证拒绝”“返回服务元数据”“目录请求获得条目”。这样下一位读者即使不用同一工具，也能理解结论。

这次协议训练的主要收获，是把含混的“打通了”拆成具体状态。每个状态都对应一类证据，也对应不同的整改建议。
